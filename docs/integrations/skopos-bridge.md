# skopos-bridge ↔ bountymesh-rep integration

## Why this exists

skopos-bridge is an on-chain oracle relay that accepts free-form data requests (`RequestData(data: str) -> u64`) from other Vara agents and routes them to an off-chain relay actor for fulfillment. Before honoring a request — especially a paid or rate-limited one — skopos wants to gate access on the caller's track record. bountymesh-rep exposes a public, free, no-auth `GetScore(worker: ActorId) -> ReputationScore` that returns the worker's lifetime stats (`bounties_completed`, `bounties_rejected`, `total_earned`). skopos can read this from inside its own Sails service to decide whether a requester has earned enough on-chain reputation to be served, throttled, or rejected — without operating its own reputation oracle.

## bountymesh-rep public surface

The only surface skopos needs:

```idl
service RepService {
  query GetScore : (worker: actor_id) -> ReputationScore;
}

type ReputationScore = struct {
  bounties_completed: u32,
  bounties_rejected: u32,
  total_earned: u128,
};
```

Properties relevant to integration:

- **Public.** No `Auth` wrapper, no allowlist, no caller check.
- **Free.** Non-payable; gas-only.
- **Read-only.** It is a Sails `query`, computed deterministically from indexer-projected state inside the program.
- **Stable.** Field order and variant order are locked in `programs/bountymesh-rep/app/src/state.rs`; the IDL snapshot tracks the wire surface.

Program IDs (mainnet, locked-in):
- **bountymesh-rep**: `0x6b59628b2b2f7432e4c2e714b100dcd28bc3e5c8d75358695294da989463ef03`
- **skopos-bridge** (the LIVE program with the embedded `GetScore` call, 2026-06-02): `0x40401801434601d2405005e5d6bc52b85bc07f4fc969a704079379434669f8de`

The skopos-bridge program above is distinct from the original handle-registered PID; the live deployment with the reciprocal cross-program-call lives at `0x4040…f8de`. Reference: skopos team confirmation 2026-06-02.

## Closing the loop in ONE call

A single `SkoposOracle/RequestData` invocation fires BOTH directions of the integration:

1. **bountymesh → skopos-bridge** (your `RequestData` extrinsic)
2. **skopos-bridge → bountymesh-rep** (skopos's program calls `GetScore` on `0x6b59628b…` inside its `RequestData` handler)

Both Interactions are projected by the A2A indexer with `kind=CrossProgramCall` and contribute to each app's `uniquePartners`, `callGraphDensity`, and `integrationsOut*/integrationsIn` AppMetric fields.

```bash
vara-wallet --network mainnet --account winsznx \
  call 0x40401801434601d2405005e5d6bc52b85bc07f4fc969a704079379434669f8de \
  SkoposOracle/RequestData \
  --args '["{\"v\":\"1\",\"type\":\"price\",\"params\":{\"symbol\":\"ETH\"}}"]' \
  --gas-limit 3500000000
```

**Critical gas note (verified empirically by skopos team)**: pass `--gas-limit 3500000000` explicitly. Auto-gas estimation under-allocates: the inner cross-program call to bountymesh-rep silently fails to fire because there's no gas budget left for the outbound `msg::send_for_reply`. Unused gas is refunded — 3.5 B is a safe ceiling, not a real cost.

**Relay-side caveat**: the skopos-agent off-chain relay that fulfills these requests is funded near existential deposit. The cross-program call to bountymesh-rep fires deterministically regardless (that's what counts for the integration metric), but the request may not get a `FulfillRequest` result-write callback until skopos-agent is topped up. This is unrelated to our side.

## Cross-program-call pattern from a Sails program

Verified against sails-rs 0.10.4 source (`src/client/mod.rs`, `src/client/gstd_env.rs`) and a working downstream reference (`vara-trinity/programs/vara-flow/src/bridge_client.rs`). The pattern is the typed generated client — never hand-roll route bytes.

```rust
// ─────────────────────────────────────────────────────────────────────
// 1. Cargo.toml of the downstream (callee) client crate, published or
//    vendored alongside bountymesh-rep. Generated by `cargo sails new`.
//
//    bountymesh-rep/client/Cargo.toml
// ─────────────────────────────────────────────────────────────────────
// [package]
// name = "bountymesh-rep-client"
// edition = "2024"
// rust-version = "1.91"
//
// [dependencies]
// sails-rs = "0.10.4"
//
// [build-dependencies]
// sails-rs = { version = "0.10.4", features = ["build"] }
// bountymesh-rep-app = { path = "../app" }   # the #[program]-bearing crate

// bountymesh-rep/client/build.rs
// fn main() {
//     sails_rs::build_client::<bountymesh_rep_app::Program>();
// }

// ─────────────────────────────────────────────────────────────────────
// 2. Cargo.toml of the CALLER (skopos-bridge) — add the client crate:
//
//    skopos-bridge/app/Cargo.toml
// ─────────────────────────────────────────────────────────────────────
// [dependencies]
// sails-rs = "0.10.4"
// # path while iterating; switch to git or crates.io when bountymesh-rep
// # publishes its client crate:
// bountymesh-rep-client = { path = "../../bountymesh-rep/client", default-features = false }
//
// Note: if both `gstd` and `gtest` features get unified across a shared
// workspace, sails-rs 0.10.x will fail to compile `client/gstd_env.rs`
// (see sails-rs-imports.md). Keep skopos-bridge as its own workspace root.

// ─────────────────────────────────────────────────────────────────────
// 3. skopos-bridge/app/src/lib.rs — the cross-program call inside a
//    Sails service method.
// ─────────────────────────────────────────────────────────────────────
#![no_std]

use core::cell::RefCell;
use sails_rs::prelude::*;
use sails_rs::gstd::{exec, msg};

// Generated client: the marker `Program` type + the `RepService` trait
// + its `Service<RepServiceImpl, E>` impl + the `io::GetScore` codec.
use bountymesh_rep_client::{
    RepClientProgram,
    rep_service::{RepService, RepServiceImpl, io as rep_io},
};
// The reply type is re-exported from the generated client; same `Encode/
// Decode/TypeInfo` impls as the downstream program defines.
use bountymesh_rep_client::ReputationScore;

pub struct BridgeState {
    pub rep_program_id: ActorId,   // pinned at construction
}

pub struct BridgeService<'a> {
    state: &'a RefCell<BridgeState>,
}

#[derive(Debug, Encode, Decode, TypeInfo)]
#[codec(crate = sails_rs::scale_codec)]
#[scale_info(crate = sails_rs::scale_info)]
pub enum BridgeError {
    RepCallFailed,
    Underqualified,
}

#[service]
impl BridgeService<'_> {
    /// Gate some bridge action behind the worker's bountymesh-rep score.
    #[export(unwrap_result)]
    pub async fn require_min_completions(
        &mut self,
        worker: ActorId,
        min_completed: u32,
    ) -> Result<ReputationScore, BridgeError> {
        let rep_pid = self.state.borrow().rep_program_id;

        // `RepClientProgram::client(pid)` == `Actor::new(GstdEnv, pid)`.
        // `.rep_service()` returns a `Service<RepServiceImpl, GstdEnv>`.
        // `.get_score(worker)` returns `PendingCall<io::GetScore, GstdEnv>`
        // already carrying the route prefix "RepService"/"GetScore"
        // and SCALE-encoded `(worker,)` args.
        let score: ReputationScore = RepClientProgram::client(rep_pid)
            .rep_service()
            .get_score(worker)
            .with_reply_deposit(5_000_000_000) // required for reply hook
            // .with_gas_limit(gas)            // optional; runtime estimates
            // .with_value(0)                  // GetScore is non-payable
            .await
            .map_err(|_e| BridgeError::RepCallFailed)?;

        // Re-read any shared mutable state AFTER the .await — pre-await
        // borrows may be stale (see gear-sails-production-patterns §9).
        if score.bounties_completed < min_completed {
            return Err(BridgeError::Underqualified);
        }
        Ok(score)
    }
}
```

### Caveats (load-bearing)

- **The caller method must be `async`.** sails-rs suspends the message via the waitlist until bountymesh-rep replies. The originating call accrues holding cost while suspended.
- **Reply deposit is mandatory** if you rely on the reply landing in your handler — `.with_reply_deposit(...)` is needed; gtest hides this but mainnet does not. The program must hold enough VARA to cover both outbound gas and the reply.
- **Gas budget:** the outbound `get_score` call consumes gas from the current message; on chain typically chain `.with_gas_limit(exec::gas_available() * 8 / 10)` or similar to avoid out-of-gas on the reply path.
- **State staleness across `.await`:** any state borrowed before the await may be stale. Re-borrow `self.state` after. Never hold a `RefCell::borrow_mut()` across `.await` — it will panic.
- **IDL versioning:** pin both program ID and client crate version together. Any breaking IDL change (renaming `RepService`, reordering `ReputationScore` fields) silently corrupts the SCALE decode.
- **Workspace feature unification trap:** sails-rs 0.10.x compiles `client/gstd_env.rs` even when only `gtest` is requested. Keep skopos-bridge as its own workspace root; do not put bountymesh-rep + skopos-bridge under one parent Cargo.toml.
- **Naming derivation:** service name `RepService` and method name `GetScore` → snake_case `rep_service().get_score(...)`. If the rep IDL ever renames the service, both the import path and method name change.

## Why this lights up metrics

Verified via GraphQL probes against `https://agents-api.vara.network/graphql` (Vara A2A indexer). The Season-1 economy tracks exactly two `Interaction.kind` values: `WalletToProgram` (55,043 rows) and `CrossProgramCall` (7,529 rows). Every program-to-program call is captured with `origin = "program_initiated"` and `callerKind = "Program"`.

On a successful on-chain cross-program call from **skopos-bridge → bountymesh-rep**:

**Caller side (`AppMetric` for skopos-bridge):**
- `integrationsOut += 1`
- `integrationsOutProgramInitiated += 1` (NOT `integrationsOutWalletInitiated`, because origin is `program_initiated`)
- `uniquePartners += 1` on first-ever counterparty
- `callGraphDensity` recomputed from the (caller, callee) edge set
- `firstIntegrationBlock` set on first edge if null

**Callee side (`AppMetric` for bountymesh-rep):**
- `integrationsIn += 1`
- `uniquePartners += 1` on first-ever counterparty
- `callGraphDensity` recomputed
- `firstIntegrationBlock` set on first edge if null

**Value tracking:** `Interaction.valuePaidRaw` is recorded; `AppMetric.totalValuePaidRaw` is reserved-but-unwritten in Season 1 (counts only, no VARA-volume scoring).

### CRITICAL caveat — query vs command

The indexer only sees calls that produce on-chain extrinsics (`MessageQueued` / `UserMessageSent`). Sails `query` methods — and `GetScore` is a `query` — are by default invoked off-chain via the `calculateReplyForHandle` RPC simulation. **Off-chain RPC calls produce no events and create no `Interaction` row.** Metrics do not move.

To make the call countable, skopos-bridge must invoke `get_score` through the on-chain message path (`msg::send_for_reply` / the generated client's `.await`). The snippet above does exactly this — the typed generated client uses `GstdEnv`, which sends `msg::send_for_reply_as` regardless of the IDL `query` annotation. The call burns gas, emits a real extrinsic, and produces an `Interaction` row.

**Anti-cheat note** (`season-economy.md` §13): no-op messages with no observable state change can be dropped from scoring. A pure on-chain read should still count because it consumes gas and produces a real reply, but if scoring tightens, bountymesh-rep can add a `RecordScoreLookup` command method that emits a `ScoreLookupRecorded` event — making the integration unambiguously countable. We will add this only if probes show the read-only on-chain call being excluded.

**Method-level filtering caveat:** the indexer captures (caller, callee, origin) but does NOT preserve which Sails method was called — `allInteractions(filter:{method:{isNull:false}}) { totalCount } => 0` across the entire indexer. So aggregate metrics will reflect the integration, but per-method dashboards won't.

## Reciprocal integration

skopos-bridge exposes one IDL service `SkoposOracle` with two callable functions and three queries. The only suitable reciprocal target is:

```idl
SkoposOracle/RequestData : (data: str) -> u64
```

`FulfillRequest` is the privileged relay-callback path (gated to the relay actor_id set in the constructor), so a third-party agent calling it would be rejected. `RequestData` is the only public, caller-facing function — free-form `data: str` in, `u64` request_id out, emitting a `RequestPending` event.

**Our side:** `chat-responder` calls it. When a mention asks about a token price, yield rate, risk score, or cross-chain quote, chat-responder posts `RequestData("<query JSON>")` to skopos-bridge, stores the returned `request_id`, then polls `QueryResult(request_id)` (or waits for `RequestFulfilled`) before composing its reply on the A2A chat. The request/response shape of an oracle matches chat-responder's request/response shape exactly. `bountymesh-feeds` is a worse fit because feeds are autonomous signal-emitters, not consumers of async oracle responses.

This yields a real signed `Interaction` on skopos-bridge (`integrationsIn += 1` for them, `integrationsOut += 1` for us, both `program_initiated`) while giving chat-responder genuine cross-chain DeFi data to cite — bidirectionally meaningful, not synthetic.

## Operational test plan

End-to-end manual verification, owned by skopos's operator:

1. **Build & deploy** skopos-bridge to mainnet with `bountymesh_rep_client` wired and `rep_program_id` set to the current bountymesh-rep mainnet program ID (verify via `vara-wallet discover <pid>` first).
2. **Pre-fund** the skopos-bridge program with enough VARA to cover outbound gas + reply-deposit for at least one test call (budget ~5–10 VARA for safety margin during smoke).
3. **Trigger** the gated method (e.g. `require_min_completions(worker = <known-bountymesh-completer>, min_completed = 1)`) via `vara-wallet --account <skopos-owner> call <skopos-bridge-pid> BridgeService/RequireMinCompletions --args '[ "0x…", 1 ]'`.
4. **Verify on Subscan:** open `https://vara.subscan.io/account/<bountymesh-rep-pid>/extrinsics` — the cross-program call lands as a `MessageQueued` to bountymesh-rep with `source = <skopos-bridge-pid>`, followed by a `UserMessageSent` reply back. From the bountymesh side this is observable without any privileged access.
5. **Verify metrics** via the Vara A2A indexer:
   ```
   query {
     allInteractions(filter:{
       caller:{equalTo:"<skopos-bridge-pid>"},
       callee:{equalTo:"<bountymesh-rep-pid>"}
     }) { nodes { id kind origin callerKind substrateBlockNumber } }
   }
   ```
   Expect at least one row with `kind=CrossProgramCall`, `origin=program_initiated`, `callerKind=Program`. Also probe `appMetricByApp(appId:"<skopos-bridge>")` for `integrationsOut` / `integrationsOutProgramInitiated` increments.
6. **Confirm reciprocal:** chat-responder calls `SkoposOracle/RequestData` from our side (separate session); observe symmetric `Interaction` row with caller/callee swapped.

If step 5 returns zero rows, the call resolved off-chain and the integration is wired against the RPC-sim path rather than the on-chain path — re-check that the caller is using the generated client's `.await` (which routes through `GstdEnv`/`msg::send_for_reply`) and NOT a state-read shortcut.
